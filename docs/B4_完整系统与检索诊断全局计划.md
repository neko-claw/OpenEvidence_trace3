# B4：完整系统与检索诊断全局计划

> 版本：v0.1
> 日期：2026-08-11
> 适用范围：赛道三 B4——完整系统与检索诊断
> 当前仓库：`OpenEvidence_trace3`

## 1. 任务定位

B4 负责把赛道一的检索/完整系统接入赛道三，并完成三类实验条件：

- **C：Rerank RAG**：评估 rerank 与 MMR 相对于基础 RAG 的增量。
- **D：完整系统**：评估 Wiki、Skill、MCP、Agent、引用审计组成的完整组件包的整体增量。
- **E：劣化 RAG**：人为降低证据质量，诊断检索失败是否拖累回答，以及系统是否能够 WARN/REFUSE。

B4 不负责：

- 重新设计赛道一的数据采集流程；
- 负责最终人工评分和统计结论；
- 对 D 中的 Wiki、Skill、MCP、Agent 做单组件因果归因；
- 在正式题上调参或修改系统使结果变好。

最终交付重点是：**可复现运行、完整候选集留痕、工具轨迹、劣化过程记录和失败案例诊断**。

## 2. 当前仓库基线

当前仓库已经具备：

- `ingestion/`：PubMed、ClinicalTrials.gov、Europe PMC 和人工指南采集；
- `data/processed/evidence.jsonl`：约 11,630 条证据记录；
- `data/processed/manifest.json`：数据集元信息；
- `artifacts/dataset_stats.*`：数据统计。

当前尚未具备：

- `retrieval/`：BM25、向量检索、RRF、rerank、MMR；
- `generation/`：统一回答生成接口；
- `evaluation/`：实验运行器、缓存、批量编排和评分接口；
- `agent/`、`skills/`、`mcp_server/`；
- Question、Qrel、Run、Score 数据文件；
- 自动化测试和 README。

开工前必须处理的已知问题：

1. 当前 `manifest.json` 记录的 `evidence.jsonl` 哈希与实际文件哈希不一致，必须重新生成或修正。
2. 当前有一部分摘要文本为空，需要隔离或标注，不能直接作为可支持证据送入上下文。
3. `pyproject.toml` 目前主要只有数据采集依赖，实验运行所需的模型、评分和测试依赖尚未冻结。

## 3. B4 的目标流水线


## 4. 工作原则

### 4.1 先用离线 fixture，再接真实系统

赛道一当前没有进展时，B4 不能等待完整系统。先用固定的 Evidence fixture、Mock Retriever 和 Mock Full System 开发运行器、日志和诊断逻辑。

### 4.2 C/D/E 的输入必须可追溯

每个候选证据都必须有稳定的 `evidence_id`，每一步都要保存：

- 查询文本和查询改写；
- 各路召回结果及排名；
- RRF 分数；
- rerank 特征分数；
- MMR 选择/淘汰结果；
- 最终上下文 Evidence ID；
- E 的扰动前后候选集；
- D 的 Skill/MCP/Agent 版本和工具轨迹。

### 4.3 只在 DEV 集调参

以下内容一旦进入 TEST 前必须冻结：

- top-k；
- rerank 权重；
- MMR 参数；
- chunk 策略；
- Prompt；
- 工具预算；
- 劣化规则；
- 语料和索引版本。

## 8. 阶段四：实现 C——Rerank RAG

### C 的固定流程

```text
BM25 Top-50
  + Vector Top-50
  ↓
RRF 合并
  ↓
特征重排
  ↓
MMR 去重
  ↓
选择最终上下文
  ↓
生成回答
```

### B4 的具体工作

1. 接入 A4 的 `search()` 或暂时使用 `ReferenceRetriever`。
2. 检查 B 与 C 是否使用相同初检候选集。
3. 保存候选证据的全部排名和分数。
4. 保存最终进入模型上下文的 Evidence ID。
5. 检查同一文献或同一来源是否占满上下文。
6. 输出检索诊断结果供 B5 计算 Hit@K、MRR、Recall@50 和 nDCG@8。
7. 在 DEV 集上比较不同 rerank 配置。
8. 冻结 `rerank_config_version` 和 `index_version`。

### C 的验收标准

- 能批量输出 C 条件 Run；
- 能证明 B/C 初检候选集一致；
- 每个候选都有排名和特征记录；
- 最终上下文可回溯到原始 Evidence；
- 调参只发生在 DEV 集；
- 失败检索能够输出原因，而不是静默生成。

## 9. 阶段五：实现 D——完整系统适配

### 目标

把赛道一的完整系统作为一个黑盒或半黑盒组件接入赛道三。

### 真实系统接入前的 Mock 阶段

先实现：

```python
MockFullSystem.run(question, config) -> FullSystemResult
```

Mock 需要返回固定格式的：

- Agent plan；
- Skill 版本；
- MCP 工具调用；
- Evidence ID；
- Claim；
- 引用审计结果；
- 回答或拒答原因。

### 真实系统接入任务

1. 接入赛道一冻结的完整系统入口。
2. 固定 Wiki、Skill、MCP、Agent 和 Prompt 版本。
3. 固定工具白名单和调用预算。
4. 保存完整 `tool_trace`。
5. 记录额外延迟、token、成本和错误。
6. 确保 D 使用与 C 相同的语料和来源白名单。
7. 不在 D 运行过程中修改系统参数。

### D 的结论边界

报告中只能比较：

```text
C：Rerank RAG
vs
D：完整组件包
```

不能将 C-D 的差异归因给某一个单独组件。

## 10. 阶段六：实现 E——劣化 RAG

### 推荐主规则

建议把“删除 gold Evidence”作为最容易复现的主规则：

1. 从 C 或基础候选集中识别 gold Evidence；
2. 删除预先规定数量的 gold；
3. 保持模型、Prompt、token 和其他参数不变；
4. 记录删除前后的候选集；
5. 观察回答是否出现错误、无依据主张或拒答。

“注入主题相关但不支持主张的证据”可以作为第二种压力模式，但不能和主规则混为一个指标。

### E 必须记录

- 扰动规则版本；
- 随机种子；
- 原始候选 Evidence ID；
- 删除或注入的 Evidence ID；
- 扰动后的候选 Evidence ID；
- 生成结果；
- 是否触发 WARN/REFUSE；
- 失败原因。

### E 的验收标准

- 同一个 seed 可得到同一个扰动结果；
- 不读取模型输出后再选择扰动方式；
- C/E 使用相同的生成参数；
- 压力题单独报告，不混入 TEST 主结果；
- 至少产出一个检索拖累或合理拒答案例。

## 11. 阶段七：批量运行与质量检查

### 推荐运行顺序

```text
Fixture：C/D/E 各 5 题
  ↓
DEV：调 top-k、rerank、MMR 和压力阈值
  ↓
冻结 system-v0.2
  ↓
TEST：运行 C/D
  ↓
STRESS：运行 C/E
  ↓
交付 B5 评分和统计
```

### 批量运行检查

- 每道题每个条件都有 Run 记录；
- 失败或超时有明确状态；
- 缓存命中和真实调用可区分；
- 输入题集哈希正确；
- 语料和索引版本正确；
- 运行时没有读取 TEST 的 gold/rubric；
- C/D/E 的调用预算没有超出协议；
- 候选证据没有出现 Evidence store 之外的 ID。

## 12. 阶段八：失败案例诊断

B4 至少准备两类案例交给 B5 和最终展示：

### RAG 获益案例

说明：

- 纯 LLM 缺少最新或专业信息；
- B/C 召回了正确 Evidence；
- C 的排序或去重改善了上下文；
- 引用支持性更好。

### 检索拖累案例

说明：

- 纯 LLM 原本能够正确回答；
- RAG 引入了主题相关但不支持主张的证据，或漏掉了 gold；
- 回答质量下降，或者系统正确拒答；
- 能定位具体的召回、rerank 或生成问题。

### 失败分类

```text
retrieval_miss
rerank_error
duplicate_context
unsupported_evidence
source_conflict
stale_evidence
generation_error
citation_error
refusal_error
system_error
```

## 14. 依赖关系和并行策略

| 工作 | 当前能否独立完成 | 最终依赖 |
|---|---|---|
| 运行器、缓存、重试、日志 | 可以 | 无 |
| Mock Retriever | 可以 | 无 |
| C 诊断框架 | 可以先做 | A4 正式检索接口 |
| D Mock | 可以先做 | A5 完整系统接口 |

```text
协议与 Schema
→ Fixture
→ Mock Retriever

→ D Mock
→ E 扰动器

→ 接入赛道一真实系统
→ 正式实验
```

## 17. B4 完成定义

B4 完成的标准不是“把完整系统全部写出来”，而是：

> 在固定数据、固定版本和固定实验协议下，B4 能稳定运行 C/D/E，完整记录候选证据和系统轨迹，能够复现劣化过程，并把结果和失败案例交给 B5 评分。

在赛道一尚未完成时，先完成 Mock 版本和诊断框架；赛道一完成后，只替换真实适配器并重新运行正式集。
